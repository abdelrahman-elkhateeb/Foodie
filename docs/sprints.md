اتعملت يوم 2026-10-28 من جولتين في الـ llm-council.

## الهدف

المشروع هيتباع لمطاعم في مصر، وكل عميل ياخد نسخة متعدّلة مخصوص ليه (white-label). لسه مفيش ولا عميل.

التغييرات هنا "آمنة": مهمة دلوقتي، ومش هتأثر على أي قرار قدام، زي الدفع أو نوع العميل أو طريقة التوصيل.

**القاعدة:** غيّر اللي الناس بتشوفه وبتحس بيه، وما تلمسش الـ data model. أي قرار عن طريقة شغل المطعم يستنى أول عميل.

## مؤجل لحد أول عميل

دي قرارات بتختلف من عميل لعميل، فما تتعملش دلوقتي:

- **الأقسام في قاعدة البيانات.** قرارات schema: أسماء بلغتين؟ ترتيب؟ لكل عميل؟ والأقسام المكتوبة في الكود سهل تتغيّر.
- **مناطق التوصيل والرسوم.** كل مطعم بيسعّر بطريقة مختلفة.
- **خيارات الأصناف (الأحجام والإضافات).** محتاجة منيو حقيقي.
- **الطلب كضيف.** بيغيّر الـ auth والـ RLS و`place_order`.
- **مواعيد العمل.** فيها شفتات وأجازات وطلبات مسبقة بتختلف من مطعم لمطعم.
- **ملف config لكل عميل.** قبل ما تشوف عميلين بيبقى تخمين.
- **PWA.** فيها قرارات caching في الـ service worker صعب ترجع فيها.
- **بوابة الدفع (Paymob / Fawry).** لما عميل يطلبها.
- **الولاء والكوبونات وشاشة المطبخ والفروع المتعددة.** لما عميل يدفع تمنها.

## على المدى الطويل (من جولة المجلس الأولى)

لما يبقى فيه عميل، الترتيب المقترح كان:

1. تنبيه صاحب المطعم على واتساب: لينك `wa.me` الأول، وبعدين WhatsApp Cloud API أو Twilio.
2. تذكرة مطبوعة مقاس 80 مم بـ `window.print()`.
3. الطلب كضيف برقم التليفون.
4. جدول مناطق `zones(name, fee, min_order)`، والرسوم تتحسب جوه `place_order`.
5. جدولين `option_groups` و`options`، وأسعارهم تتحسب جوه `place_order`.
6. كود واحد، ومن غير fork لكل عميل. لكل عميل مشروع Supabase ومشروع Vercel، وسكريبت واحد يشغّل الـ migrations على كل المشاريع.

**التسعير:** رسوم تجهيز مرة واحدة، ورسوم شهرية تغطي الاستضافة والدعم.
